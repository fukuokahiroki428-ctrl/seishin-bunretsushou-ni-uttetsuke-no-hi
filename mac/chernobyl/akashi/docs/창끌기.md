# 창 끌기 — 창 서버에 맡긴다 (`757d52d`)

사용자: "클로드 창 이동할때는 렉 없이 부드럽게 이동되는데 우리꺼 한이시키는 딜레이가 있고 렉도 있네".

## 무엇이 문제였나

앱이 **8ms 타이머로 창을 직접 옮기고** 있었다(`startDragTimer` → `move()`). 화면 갱신과 박자가 안 맞고, 수집 중엔
메인 스레드가 바빠 밀렸다. 클로드 창(Electron)은 끌기를 macOS **창 서버**에 맡긴다 — 앱이 바빠도 창은 부드럽다.

## 헛디딘 것 — 흉내 낸 누름은 무시된다

`performWindowDragWithEvent:` 는 **지금 들어와 처리 중인 진짜 마우스 누름**을 받아야 한다. 나중에 NSEvent 를 만들어
넘기면 창 서버가 조용히 무시한다. 처음 두 빌드가 여기서 헛돌았다("존나 부드럽습니다라고 할 줄 알았지?").

## 지금의 짜임 (`src/core/MainWindow.cpp`)

1. `WindowDragFilter` — `QAbstractNativeEventFilter` 가 `mac_generic_NSEvent` 의 왼쪽 누름을 **Qt 가 처리하기 전에** 본다.
   끌 자리면 그 진짜 이벤트를 곧장 `performWindowDragWithEvent:` 에 넘기고 삼킨다(`installWindowDragFilter()`, 생성자에서).
2. '끌 자리' 판단은 두 길이다(`pointInDragZone()`).
   - **좌표** — 화면 JS `publishDragRegions()` 가 사이드바 · 위 띠의 사각형과 그 안의 단추 자리(구멍)를
     `backend.setDragRegions(열쇠, json)` 로 넘긴다. 뒤에 있던 창을 앞으로 가져오는 **첫 누름**엔 아직 마우스 움직임
     신호가 없으므로 좌표가 필요하다. 열쇠는 `#window=<탭>`(기능 창) 또는 `main` — 창마다 따로(`ced5af7`).
   - **움직임 신호** — 마우스가 빈 바탕 위에 있으면 JS `setHover` 가 `backend.setDragHover(true)` 를 보낸다(바뀔 때만).
     끌 수 있는 바탕: `.scroll-area, .tab-content, .main, .app, .settings-board, .sg, .settings-filter, .fx-board, .fx-bar`.
3. 가장자리 6px(크기 조절)과 신호등 단추(NSButton)는 건드리지 않는다.
4. 네이티브 길이 1.5초 안에 안 탔으면 옛 타이머(`armWindowMove`)가 예비로 돈다 — 드물다.

## 확인하는 법 — 사람이 끌어야 한다

이 맥은 손쉬운 사용 권한이 없어 OS 마우스를 흉내 낼 수 없다. 그래서:

```bash
python3 akashi/iso.py start
python3 akashi/drag_watch.py              # 안내에 따라 사이드바·위 띠·빈 바탕을 끌어 본다
python3 akashi/drag_watch.py --anywhere   # 판단(좌표·신호)을 떼고 네이티브 필터만 시험
```

기록 줄의 뜻:
- `[창 끌기] 끌 자리 N곳 · 단추 자리 M곳 받음 (main)` — 좌표가 들어왔다.
- `[창 끌기] 창 서버에 맡김` — 부드러운 길을 탔다(처음 세 번만 적힌다).
- 끌었는데 이 줄이 없으면 예비 타이머 길이다. `--anywhere` 로도 굼뜨면 네이티브 필터 쪽, 부드러우면 판단 쪽을 본다.

## 윈도우에서는

`performWindowDragWithEvent:` 는 맥 전용이다. 윈도우의 같은 길은 `ReleaseCapture()` + `SendMessage(hwnd, WM_NCLBUTTONDOWN, HTCAPTION, 0)`
또는 Qt 의 `QWindow::startSystemMove()` 다. 좌표·신호로 '끌 자리' 를 가리는 화면 쪽은 그대로 쓸 수 있다.
